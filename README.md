## Problem Statement

Your employer has recently purchased a license to top-tier SaaS platform, Employees-R-US, to off-load all employee management responsibilities.
Unfortunately, your company's product has an existing employee management solution that is tightly coupled to other services and therefore 
cannot be replaced whole-cloth. Product and Development leads in your department have decided it would be best to interface
the existing employee management solution with the commercial offering from Employees-R-US for the time being until all employees can be
migrated to the new SaaS platform.

Your ask is to expose employee information as a protected, secure REST API for consumption by Employees-R-US web hooks.
The initial REST API will consist of 3 endpoints, listed in the following section. If for any reason the implementation 
of an endpoint is problematic, the team lead will accept **pseudo-code** and a pertinent description (e.g. java-doc) of intent.

Good luck!

## Endpoints to implement (API module)

_See `com.challenge.api.controller.EmployeeController` for details._

getAllEmployees()

    output - list of employees
    description - this should return all employees, unfiltered

getEmployeeByUuid(...)

    path variable - employee UUID
    output - employee
    description - this should return a single employee based on the provided employee UUID

createEmployee(...)

    request body - attributes necessary to create an employee
    output - employee
    description - this should return a single employee, if created, otherwise error

## Solution Overview

The API uses a controller and service-layer design with a thread-safe, in-memory employee store. Employee UUIDs and
default hire dates are generated by the service. Because the challenge does not require persistence, employee data is
reset whenever the application restarts.

The create endpoint validates required names, job title, email, non-negative salary, a reasonable age, and contract
date ordering. Invalid requests return HTTP 400, missing employees return HTTP 404, and successful creation returns
HTTP 201.

### Design Decisions

I kept the controller small so it only translates HTTP requests and responses. Employee creation and lookup live in
the service, which makes those rules easier to test and keeps them independent of the web layer. For storage, I chose
a `ConcurrentHashMap` because the prompt specifically says a real persistence layer is not required. It also handles
multiple requests more safely than a basic mutable map.

UUID and full name are generated by the service instead of accepted from the request. This keeps system-owned values
consistent and prevents a client from supplying a full name that disagrees with the first and last names.

### Production Considerations

The challenge describes a protected webhook API but does not specify an authentication mechanism or how credentials
are issued. Rather than embed a default password or invent an incompatible contract, this implementation leaves
authentication configuration to the integrating system. A production version should authenticate webhook requests
using the agreed mechanism (for example, signed requests or mutual TLS), store employee data in persistent storage,
and avoid logging sensitive employee fields.

## Run Locally

The project requires JDK 17 and includes the Gradle wrapper, so a separate Gradle installation is not needed.

```shell
./gradlew clean build
./gradlew :api:bootRun
```

The API is available at `http://localhost:8080/api/v1/employee`.

Create an employee:

```shell
curl -X POST http://localhost:8080/api/v1/employee \
  -H 'Content-Type: application/json' \
  -d '{
    "firstName": "Ada",
    "lastName": "Lovelace",
    "salary": 100000,
    "age": 36,
    "jobTitle": "Software Engineer",
    "email": "ada@example.com"
  }'
```

List employees with `GET /api/v1/employee` or retrieve one with `GET /api/v1/employee/{uuid}`.

## Tests
