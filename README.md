## Problem Statement

Your employer has recently purchased a license to top-tier SaaS platform, Employees-R-US, to off-load all employee management responsibilities.
Unfortunately, your company's product has an existing employee management solution that is tightly coupled to other services and therefore 
cannot be replaced whole-cloth. Product and Development leads in your department have decided it would be best to interface
the existing employee management solution with the commercial offering from Employees-R-US for the time being until all employees can be
migrated to the new SaaS platform.

Your ask is to expose employee information as a protected, secure REST API for consumption by Employees-R-US web hooks.
The initial REST API will consist of 3 endpoints, listed in the following section. If for any reason the implementation 
of an endpoint is problematic, the team lead will accept **pseudo-code** and a pertinent description (e.g. java-doc) of intent.

Good luck!

## Endpoints to implement (API module)

_See `com.challenge.api.controller.EmployeeController` for details._

getAllEmployees()

    output - list of employees
    description - this should return all employees, unfiltered

getEmployeeByUuid(...)

    path variable - employee UUID
    output - employee
    description - this should return a single employee based on the provided employee UUID

createEmployee(...)

    request body - attributes necessary to create an employee
    output - employee
    description - this should return a single employee, if created, otherwise error

## Solution Overview

> This repository preserves the original assessment prompt above. The sections below document my implementation, design choices, and verification steps.

The API uses a controller and service-layer design with an in-memory employee store backed by a `ConcurrentHashMap`. Employee UUIDs and default hire dates are generated by the service. Because this OA does not require persistence, employee data resets whenever the application restarts.

The create endpoint validates required names, job title, email, a non-negative salary, a reasonable age, and contract date ordering. Invalid requests return HTTP 400, missing employees return HTTP 404, and successful creation returns HTTP 201.

### Design Decisions

I kept the controller small so it only translates HTTP requests and responses. Employee creation, validation, and lookup live in the service, which makes those rules easier to test and keeps them separate from the web layer. For storage, I chose a `ConcurrentHashMap` because the prompt says a real persistence layer is not required. It works well for this small exercise and keeps map operations safe when requests arrive at the same time. The main tradeoff is that all employee data resets when the application restarts.

The service generates the UUID and full name, and it supplies a hire date when the caller omits one. It also trims text input before storage so names, titles, and email addresses remain consistent.

### API Behavior

| Request | Successful result | Error behavior |
| --- | --- | --- |
| `GET /api/v1/employee` | Returns every employee, or an empty list before any are created | N/A |
| `GET /api/v1/employee/{uuid}` | Returns the matching employee with HTTP 200 | Returns HTTP 404 when the UUID is unknown |
| `POST /api/v1/employee` | Validates input, creates the employee, and returns HTTP 201 | Returns HTTP 400 when the request is invalid |

### Production Considerations

The OA describes a protected webhook API but does not specify an authentication mechanism or how credentials are issued. Instead of embedding a default password or inventing an incompatible contract, my implementation leaves authentication configuration to the integrating system. A production version should authenticate webhook requests using the agreed mechanism—for example, signed requests or mutual TLS—store employee data in persistent storage, avoid logging sensitive employee fields, and use a shared error-response format for clients.

## Run Locally

The project requires JDK 17 and includes the Gradle wrapper, so a separate Gradle installation is not needed.

```shell
./gradlew clean build
./gradlew :api:bootRun
```

The API is available at `http://localhost:8080/api/v1/employee`.

Create an employee:

```shell
curl -X POST http://localhost:8080/api/v1/employee \
  -H 'Content-Type: application/json' \
  -d '{
    "firstName": "Ada",
    "lastName": "Lovelace",
    "salary": 100000,
    "age": 36,
    "jobTitle": "Software Engineer",
    "email": "ada@example.com"
  }'
```

List employees with `GET /api/v1/employee` or retrieve one with `GET /api/v1/employee/{uuid}`.
